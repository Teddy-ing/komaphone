# Komaphone GCP hosting and Google sign-in

Baseline 1.4, 2026-11-08. This is the implementation contract for product H1-H4, not a deployed-service runbook or evidence of working remote play. Read the [product specification](product-spec.md), [architecture](architecture.md), [delivery plan](delivery-plan.md), and [status](status.md). The owner selected GCP, Google sign-in, and K6.5 before K7; target USD $20/month or less, with approximately $30/month acceptable. No infrastructure is provisioned by this documentation change.

## Intended experience and deployment

Friends install the Windows app, choose Sign in with Google, authenticate in their normal browser, and return to Komaphone. An admitted friend accepts an invitation and joins a game or selected canvas. The normal connection needs no VPN, home-router changes, developer console, pasted bearer token, or certificate-file import. Ship a configured service endpoint with an explicit advanced override for development. The editor automation/control endpoint remains loopback-only.

Use one small Linux Compute Engine VM in a suitable US region as the initial deployment. Start the capacity evaluation with e2-small (2 GiB RAM); compare e2-micro only if measured service workload and recovery have adequate headroom. This is a resource decision, not a canvas-member cap. The Windows clients remain native Rust/egui/wgpu; server Linux packaging does not change the desktop platform. Use the existing Rust room/sync service and a single service writer owning its SQLite database on persistent disk. Client-side rendering/export should remain on clients where already designed; measure any service-side image/replay work explicitly.

Provide a DNS hostname and automatically renewed publicly trusted HTTPS, a service supervisor with boot/restart behavior, bounded logs, health/readiness checks, least-privilege execution and a narrow network surface. Choose a compatible TLS termination route during the K6 spike; the current non-loopback service requires TLS, so do not assume an unencrypted public bind or weaken that safeguard. Keep administrative access separate from gameplay. Do not add Kubernetes, a managed database, load balancer, autoscaling fleet, or paid authentication service without a measured requirement and an updated cost estimate. A single VM is not high availability: outages leave local work safe and sync visibly pending.

A VM fits the existing durable filesystem/SQLite service. Cloud Run's default writable filesystem is instance-local and nonpersistent; moving to it would require a separately verified durable-storage design, not simply copying the existing database into a container. See Google's [container filesystem contract](https://docs.cloud.google.com/run/docs/container-contract#file_system).

## Google identity, linking and authorization

- Use standards-based desktop OAuth/OIDC with the system browser, authorization-code flow and PKCE, one-use state/nonce and a bounded loopback callback. Do not embed a webview or treat an installed-app client secret as confidential. Follow current [Google desktop authentication documentation](https://developers.google.com/identity/protocols/oauth2/native-app).
- The service validates the identity token's signature against trusted Google keys, issuer, intended audience, expiry and the login transaction binding before issuing a Komaphone session. Reject arbitrary caller-provided identities, replayed login transactions and wrong-audience/expired tokens. Bound remote discovery/key-fetch behavior and fail safely during outages. See [Google's backend verification guidance](https://developers.google.com/identity/sign-in/web/backend-auth).
- Map the verified `(issuer, subject)` to an internal stable profile ID. Keep device writer IDs distinct from account IDs; names and emails are labels, not stable authorization keys. Authentication identifies a person; private service admission and current room/canvas membership decide access. Google sign-in alone must not allow arbitrary users to enroll or list artwork. Use explicit admin admission or a scoped, expiring invitation redeemed by the signed-in account; keep service admission distinct from canvas membership and avoid a privileged person who must own every canvas.
- Link an existing installation using both a verified new login and proof of the existing local/service profile credentials. Back up and version the migration; preserve canvas/project IDs, accepted credits, memberships, device sequence allocation, pending edits and recovery variants. Reject takeover, conflicting links and account merges that cannot prove authority. Never silently reassign ownership from an email/name match. Imported archives retain provenance but cannot assert live account ownership.
- Keep application sessions revocable, expiring and device-scoped where appropriate. Store durable credentials through Windows-protected credential services behind platform adapters; redact credentials from URLs, logs, screenshots, ordinary settings and exports/archives. Request only sign-in scopes; do not request Drive/Gmail access. Avoid retaining provider refresh tokens if the selected flow does not need them.
- Sign-out stops authenticated network work and clears credentials as appropriate without deleting drawings. Account switching isolates caches, private views and pending queues; a new account cannot upload the old account's edits. Previously downloaded artwork is not remotely erasable, and this is not protection against another person with full filesystem access. Expired login, cancellation and provider/network failure leave local drawing/recovery usable and expose an actionable reconnect flow.
- Keep auth/native networking behind the engine/service seam and platform boundaries so existing WASM compilation remains valid. New auth actions use documented stable `komaphone.*` command IDs, enabled/authorization rules and adversarial-input tests.

Sources consulted 2026-11-08: [Compute Engine VM pricing](https://cloud.google.com/products/compute/pricing/general-purpose), [external IPv4/network pricing](https://cloud.google.com/vpc/network-pricing), and [persistent disk/snapshot pricing](https://cloud.google.com/compute/disks-image-pricing). The implementation agent must refresh these rates rather than treating this snapshot as permanent.

Add off-VM backup storage/requests, outbound traffic, logging/monitoring, DNS/domain registration or renewal, and applicable taxes to the full estimate. Include expected light-use and higher-traffic scenarios, disk growth and backup retention. List every billable resource; show monthly amortization for annual costs. Google sign-in need not introduce a paid auth layer; if Identity Platform is selected, verify its integration and current [pricing](https://cloud.google.com/identity-platform/pricing) rather than assuming all authentication options have the same cost.

Aim for <=$20/month total. A justified configuration around $20-$30/month is within the owner's stated preference; do not repeatedly ask to reconfirm that range. If the forecast materially exceeds approximately $30/month, present the measured reason and a cheaper workable option before incurring additional recurring spend. Check the owner's GCP credits, applicable services, project eligibility and expiry; report the normal pre-credit run rate as well as the expected billed amount. Credits are not permission to build an expensive deployment.

Configure budget alerts around $20 and $30 and bounded log/backup retention, upload/request rates and storage growth. Alerts do not cap spend or stop resources; see [Google Cloud budget guidance](https://docs.cloud.google.com/billing/docs/how-to/budgets). Do not implement a surprise shutdown or delete accepted artwork to enforce the budget. At a storage limit, reject growth clearly and preserve locally queued work. Record actual usage and a projected monthly total after the acceptance workload, with its observation duration and uncertainty; a short test is not a month-long cost measurement.

## Delivery split

### K6 foundations

Before freezing shared-canvas identity schemas, implement and test the account/profile/device boundary and reversible linking migrations. Test with a local identity-verification adapter as needed, clearly labeled as test-only. Prove an isolated Linux service build/start, persistence/restart and the proposed TLS/proxy arrangement locally; measure representative memory/CPU, storage and traffic. Prepare repeatable deployment/configuration assets, resource inventory, current estimate and a Google OAuth project/client setup checklist. Do not let missing cloud credentials block independent K6 drawing/sync work. Actual Google login, GCP provisioning and independent-public-network acceptance belong to K6.5; no local mock counts as that proof.

### K6.5 hosted friend access

Verify K6 and existing K4 party evidence, then finish native Google login and private admission, safe account linking, service/client packaging and the operational runbook. Prepare a reviewable deployment with project/region, resource sizes, expected monthly costs, hostname/TLS, credentials/IAM requirements, migrations/backups, and rollback. This request authorizes planning/preparation and the stated budget preference; it does not select a billing project, grant account access or launch infrastructure now. When executing K6.5, use applicable authorization already present; obtain only genuinely missing project/access/deployment decisions after completing independent preparation. Do not ask again whether to use GCP, Google login or the agreed budget range.

Deploy when concretely authorized and access exists. Supply one-time administrator setup, friend quick-start, update/rollback and recovery instructions with tested commands. Keep secrets out of tracked configuration. Back up consistent database state and every referenced asset to a separate durable location off the VM; retention must be bounded and documented. Verify restoration to a fresh service with isolated test data and no destructive replacement of the live service. Exercise certificate renewal, startup after reboot and session behavior after restore. Record the protocol/schema versions supported by the packaged client.

Required acceptance evidence:

1. Packaged Windows clients on independent public internet connections sign in through Google and join via the normal configured HTTPS route. The owner-approved network clarification accepts home broadband plus a cellular hotspot with phone Wi-Fi disabled for K6.5 even in one home; fresh friend onboarding from another household remains a K7 gate. No VPN, custom root certificate, firewall/router workaround on the clients' PCs or developer credential-pasting. Record build/service versions and the exact network arrangement without claiming different-household onboarding or exposing credentials or unnecessary personal details.
2. Finish both Animation and Exquisite Corpse with those clients, then close/reopen, reveal, replay and export. Preserve the existing two-/three-player automated coverage; use a third real client for the three-player remote flow when available, and label any unexercised configuration precisely.
3. Disconnect/reconnect during drawing, submission and reveal; restart the service; retain assignment/identity and every acknowledged save. Exercise expired/revoked sessions, canceled login and clear retry behavior rather than a permanently disabled Connect control.
4. Create independently shared canvases, test a non-owner editor and a denied nonmember, draw simultaneously, then have A sync and shut down before B signs in and continues. Repeat offline edits/reconnect and account switching; verify canonical convergence, author-local undo, isolation, tours/catch-up/remix and saved review state. Retain K6's >4-member fixtures without confusing them with the two-/three-player party limit.
5. Restore an off-VM backup into a fresh isolated service and verify rooms, canvas ownership, accepted art/assets and revisions; the original service/data remain intact. Test renewal/restart and interrupted backup/upload failure behavior. Reconcile session revocations and invite expiry safely on restoration rather than blindly resurrecting access.
6. Inspect the actual sign-in, invitation, reconnect/error and account-switch UI. Run AGENTS.md required checks for changed crates, invalid-token/linking/session tests and bounded-input/resource tests. Record capacity, expected monthly cost, limits and all external evidence in status.

Missing Google/project access, deployment authorization or real independent-network clients leaves the corresponding K6.5 gate pending, not passed. Complete independent implementation/testing and report exactly what is missing. K4 home-LAN results and the unsuccessful remote attempt are not a substitute. K6.5 cannot be marked complete using only local adapters or deployment scripts.
