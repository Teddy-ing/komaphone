This is implementation guidance, not a change to the product baseline or a claim of Endless Paper feature parity. ## Distinguish the three problems

1. **Input sampling:** dropping intermediate positions can turn a fast curved gesture into a few long straight segments. Preserve available real movement events before considering invented/interpolated samples.
2. **Path smoothing:** fitting or filtering the centerline can remove hand wobble, including mouse wobble, but changes what was drawn. It should be intentional and must not silently rewrite or reinterpret old saved artwork.
3. **Rendering:** joins, caps, polygon approximation and edge coverage determine how a fixed path appears. A rounded brush requires continuous, correctly joined coverage even when magnified. More input samples or a pen cannot repair a renderer's broken coverage.

The screenshot alone does not prove which renderer defect produced its square steps. The large rectilinear protrusions are a reason to test geometry and clipping separately from input smoothing. They are not evidence that the mouse is inherently incapable of smooth drawing.

## Bounded implementation recommendation

Preserve the existing retained stroke points, scale anchors, widths, colors and serialized format. First reproduce the user's shapes with synthetic curved and sharply turning centerlines, then compare the actual output against the round-brush envelope. At ordinary projected widths, an explicitly round joined mesh or the union of round-ended segment capsules implements the same stored centerline. A capsule approach must account for overlapping edge coverage; independently alpha-blending semitransparent capsules is not a general solution for future translucent brushes.

Refine circular outlines according to their error in screen pixels, rather than a fixed polygon count or a tolerance in the original drawing coordinates. Retain relative-origin/high-precision projection and viewport clipping before final GPU coordinates. At extreme ancestor scales, refine only the arc visible in the viewport; constructing a complete enormous circle would defeat the resource bounds. Keep aggregate geometry limits and report exhaustion safely instead of silently deleting detail or removing a limit.

Antialiasing handles the last fraction of a pixel at an otherwise correct boundary; it cannot fix a coarse or incorrectly joined outline. Likewise, fitting a smooth centerline through every saved stroke would change corners and artwork and is not required for clean round joins. Optional new-stroke smoothing can be evaluated separately after the renderer is correct and input events are preserved.

## Evidence required from the implementation

- Inspect before/after native-rendered images of the same stored stroke at several zooms, including wide turns, repeated points, reversals, dots, clipped endpoints, viewport-crossing ancestors, eraser passes and high DPI.
- Compare filled coverage to a round-brush geometric oracle within an explicit screen-space tolerance. Check sharp turns and near-collinear segments; a screenshot alone is not an oracle.
- Prove saved points/widths are unchanged across the renderer change and reopen. Prove available input moves remain ordered and the mouse-up endpoint is retained.
- Keep geometry work bounded and measure the existing dense-scene acceptance workload. Run touched-crate, clippy, layer and WASM gates plus the repository's required hot-path checks.

No external code, shaders or assets were copied. No paid service, deployment, new library or baseline change is requested by this research.

## Bounded display simplification: researched and implemented

Native measurements of the initial round-mesh implementation showed a material frame-time regression at the full source-point limit. The coordinator therefore integrated the researched display-only approximation in [round/simplify.rs](../../crates/scene/src/round/simplify.rs) through [round.rs](../../crates/scene/src/round.rs). Authored samples and the serialized representation remain unchanged, and every new zoom is evaluated against those original samples. The status ledger owns final acceptance; the CPU diagnostic below is not a native-frame or input-latency claim.

The Rust [geo 0.33.1 `Simplify` documentation](https://docs.rs/geo/0.33.1/geo/algorithm/simplify/trait.Simplify.html) describes Ramer–Douglas–Peucker simplification with a distance tolerance, and expressly warns that it does not preserve topology. [CGAL's polyline simplification manual](https://doc.cgal.org/latest/Polyline_simplification_2/) describes measuring error against the original subpolyline and a finite replacement segment, and retaining original points for subsequent measurements. These support error-bounded approximation; neither is evidence that topology, traversal order, brush opacity or arbitrary curve shape can be preserved by unrestricted simplification.

For the current opaque, constant-width brush, the implemented display-only allowance is at most **0.125 physical pixel** of centerline approximation, added to the existing **0.125 physical pixel** circular-outline approximation allowance. This is a geometric approximation budget, not a claim that antialiased pixel colors are identical or that physical display pixels can resolve every subpixel feature. Keep the tolerance fixed in physical display units; do not increase it when work or geometry limits are reached.

Use the distance from each original intermediate point to the **finite replacement segment**, including clamping the projection to both endpoints. Infinite-line distance incorrectly removes the excursion in `(0, 0) → (10, 0) → (5, 0)`. Coincident endpoints require point distance, so a visible closed loop cannot disappear merely because its start and end match. Work in the already projected local screen coordinates using `f64` calculations; retain original endpoint indices rather than manufacturing new source points.

The following bound is our mathematical reasoning, not a quoted library guarantee. When every original vertex in an interval is within epsilon of its replacement segment, each connecting original edge also lies in that segment's convex epsilon capsule. The whole original interval is therefore within epsilon of the chord. Conversely, continuity of the original interval's projection from the chord's start to its end means every chord position has an original-path point with the same projected coordinate and distance at most epsilon. Thus the two traces have symmetric Hausdorff distance at most epsilon, including reversals and loops; the degenerate chord is the corresponding disk case. Taking unions preserves this bound. Distance to the two centerlines consequently differs by at most epsilon, which bounds the constant-radius brush's distance-based coverage region. This does **not** preserve subpixel topology or how many times a path retraces itself; opaque static rendering is the relevant scope. Stored traversal, replay and any future variable-width or translucent brush must keep their original semantics.

Use a deterministic iterative interval stack with a budget of `32 * N` point-to-segment distance evaluations, plus bounded linear bookkeeping. Only replace an interval after its complete error scan passes. On budget exhaustion, retain every original point in that unfinished interval and all remaining intervals. Pending intervals have disjoint interiors, so this fallback remains linear. Previously accepted intervals stay within tolerance, and fallback intervals have zero approximation error. This guarantees bounded work without silently coarsening geometry or losing source samples. Cache decisions must include viewport/zoom and display density; never repeatedly simplify a previous approximation.

Regression oracles and verification obligations:

- Verify each replacement chord against **every original vertex in its source-index interval** using an independent finite-segment distance calculation; endpoints must match and retained indices must remain ordered.
- Exercise collinear overshoot and reversal, repeated points, zero-length paths, coincident-endpoint circles, hairpins, self-crossings, tiny loops on either side of the tolerance, clipped paths, and extreme supported display densities.
- Force a tiny work budget in a test seam and prove unfinished intervals are copied exactly, evaluation count stays within the budget, and the same geometric oracle still passes. Test deterministic tie handling.
- Check brush coverage against the original polyline's distance field outside the combined approximation/antialias transition band. Inspect zoom steps for popping and confirm fine detail reappears from the retained originals when magnified.
- Re-run ordinary and full-source-capacity CPU benchmarks and native frame measurements; record generated vertices, memory and timing without reducing the source-point limit. Keep schema/save/reopen equality checks.

The consuming mesh builder removes adjacent duplicate positions again after simplification: a subpixel closed loop can legitimately reduce to coincident original endpoints, which must become a dot rather than an invalid zero-length direction. Independent review identified this integration condition before acceptance.

The retained [candidate 3 CPU diagnostic](../../log/k5-lines/round-bench-candidate3-diagnostic.json), produced by [round_bench.rs](../../crates/scene/examples/round_bench.rs), exercised all 131,072 source points as sixteen 8,192-point curves. It generated 44,112 vertices and 95,472 indices, occupying 911,232 payload bytes and 1,179,648 bytes of allocated vector capacity. The previous [candidate 2 diagnostic](../../log/k5-lines/round-bench-candidate2-diagnostic.json) generated 1,690,953 vertices with 50,331,648 allocated-capacity bytes for that same fixture. Source and executable hashes are retained in the [candidate 3 artifact record](../../log/k5-lines/round-bench-candidate3-artifact.json). Those diagnostic timings may overlap compilation work.

Final [release CPU measurements](../../log/k5-lines/perf-20261108T194508Z/round-bench.json), taken after owned builds finished, passed all six cases: the full-source width64/density2 fixture measured p95 7.8223ms with the same 44,112 vertices. This is CPU tessellation, not frame or input latency. The separate width5/density1 native capacity fixture rendered and recovered all 131,072 samples with frame-interval p95 24.887ms against 33ms. Native before/after pixel checks, saved-data equality, full affected tests, independent visual review and limitations are recorded in the completed [status handoff](status.md). These measurements do not claim host exclusivity or undisclosed proprietary behavior.
