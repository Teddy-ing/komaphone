## Reviewable resource plan

Proposed initial region **us-central1**, zone **us-central1-a**, subject to measured latency and actual availability. Use one regular, non-Spot **e2-small** (2 GiB RAM, shared CPU) with Debian 12 or another verified nonpremium Linux image. Build the service off the VM. A separate **10 GiB pd-standard boot disk** and **20 GiB pd-standard data disk** isolate releases from durable art. Set the data disk's auto-delete flag false. The initial service growth quota is **2 GiB**, leaving room for recovery, migration copies and logs; it is an operational limit and not a canvas membership cap.

Allocate one regional external IPv4 and a dedicated VPC/subnet. Allow inbound TCP 80/443 to the tagged service VM; allow SSH 22 only from Google's IAP range `35.235.240.0/20`, with OS Login and administrator IAM. Do not open 43127 or the desktop control port. No load balancer, NAT gateway, Kubernetes, managed database, CDN, or paid auth platform is included. Private admission must be enforced in the hosted service before public exposure; current legacy pairing is not a substitute for that gate.

The owner offered the existing domain **tedsoftware.org**; the selected service hostname is **komaphone.tedsoftware.org**. Use its owner-confirmed Namecheap DNS provider, with no new Cloud DNS zone or domain purchase. Preserve all existing records, especially `www`; a future `komaphone` A record waits for the specifically authorized deployment's static IP. Caddy obtains/renews public certificates on the VM, then proxies to Rust on **127.0.0.1:43127**. The existing service refuses non-loopback plaintext; this arrangement preserves that check. Caddy's administration port stays loopback-only. [Caddy's documented HTTPS route](https://caddyserver.com/docs/automatic-https) requires the hostname's DNS records, public 80/443 reachability and persistent certificate storage. A local test CA proves proxy plumbing only; public trust/renewal remains an external K6.5 check.

The native binary runs as a dedicated `komaphone` user under systemd. Templates in [k6-deploy](../../scripts/komaphone/k6-deploy/linux-build.sh) include the unit, proxy configuration and bounded journal settings. Only `/var/lib/komaphone` is writable to the service; retain Caddy certificate state separately. The service's existing shutdown handler uses SIGINT, which the unit specifies. Readiness is checked by the actual `/health` endpoint after process startup; a successful systemd start alone is insufficient. No access-body/header logging is enabled.

Create one private, uniform-access Standard GCS bucket in the same region for verified backups. Grant the VM's dedicated service account **Storage Object Creator on that bucket only**, with no project-wide editor/admin role and no downloaded service-account key. Restoration uses a separately authorized administrator. Daily unique backup objects expire after 8 days; retain the bucket's 7-day soft-delete protection. At most roughly 16 daily full 2 GiB backups including deletion lag fit the 32 GiB planning allowance; growth/failed lifecycle changes require review. Full backups retain the SQLite-contained immutable assets with metadata. Before publishing a new storage schema, recheck that every referenced blob still travels with the backup.

## Deployment, backup and rollback sequence

1. Freeze/hash the tested Linux binary and Windows package. Record schema/protocol versions, compatible rollback binary, configuration hashes and the precise GCP project/resource inventory. Finish public admission before exposing the existing RPC interface.
2. After the specific project/hostname/deployment is authorized, provision only the listed resources. Mount the data disk by stable UUID; verify filesystem ownership and mount before starting service. Install versioned immutable binaries under `/opt/komaphone/releases/<version-hash>` and point `current` to the approved release. Provision users, unit and Caddy using reviewed configuration, without storing credentials in templates.
3. Verify local health, TLS hostname/public trust, restricted ports, restart and reboot. Verify first backup with `photocraft-sync --data-dir /var/lib/komaphone --backup-to <new-path>` and upload the verified file to the private bucket. A completed upload alone is not restore proof.
4. Restore a downloaded backup using `--restore-from` into a **fresh empty** directory. Run an isolated instance on a different loopback port, exercise rooms/assets/canvas ownership and revisions, and reconcile revocations/invite expiry against the live authority. Never run an older binary against a newer schema or overwrite the live directory.
5. Before an update, take a verified backup and keep the prior release/configuration. Stop accepting new writes during a schema transition. If startup/health fails before new writes are accepted, stop the failed unit, repoint to the compatible prior binary and restore the pre-upgrade backup into a new data directory if required. Preserve the failed database for diagnosis. If new writes were accepted, retain them and use a forward repair/migration; restoring an old backup would lose acknowledged work.
6. To undo infrastructure testing, first verify a restorable off-VM backup and retained local art. Disable gameplay exposure, stop/delete only explicitly identified test resources, preserve the data disk/backups until owner review, and release unused external addresses/DNS only when no longer needed. A stopped VM alone is not a zero-cost rollback. No destructive rollback is automated here.
