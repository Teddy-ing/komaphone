## Controlled activation and hosted checks

Plan a **10-minute maintenance window** as an operational target, not a measured availability guarantee. The installed unit allows45seconds orderly stop,30seconds readiness,5seconds restart delay and5 starts per60seconds. An operator must watch the change; record stop/start/readiness timestamps. Decide within2minutes of unsuccessful local readiness whether to repair a bounded configuration error or enter recovery. Do not repeatedly restart a migrating service or automatically launch an old binary. If recovery cannot safely fit the window, keep the proxy closed and tell participants to continue local drawing; elapsed time never authorizes data loss.

It stops Caddy and the Rust writer, records `previous-release.txt`, creates a verified **stopped-service** pre-update database backup with the prior binary, records `pre-update-backup.txt`, changes the release link, installs pinned units and starts the new service. The new startup may migrate the database. Caddy stays stopped on success or failure. The script starts the backup timer on success; keep that timer paused again until the checks below complete. Retain all release and backup pointers even on failure; never overwrite an existing release directory to retry.

With Caddy still stopped, verify schema4, migration-backup pin/integrity, hosted client-ID readiness, loopback-only binding, acknowledged world/art receipts, identity/device linkage and current member/nonmember authority. Test valid old canvas envelopes426/version and malformed envelopes400 without reflecting payloads. Verify service memory/storage behavior remains within the existing unit/quota bounds. Do not use synthetic sessions in the production database. A healthy process alone is insufficient.

Validate the **existing** Caddy configuration and start Caddy only after local checks pass. No firewall/DNS/TLS reconfiguration is expected. Through ordinary trusted HTTPS, test the pinned new client: real Google sign-in/admission, existing linked identity and accepted art, denied nonmember, independent canvas ownership, shared drawing/reconnect, archive import with source unavailable, tours/catch-up/remix and both party modes. ## Failure and rollback procedure

The safe rollback tuple is **prior binary + prior compatible configuration/units + verified pre-upgrade schema3 backup**. Never point an old binary at schema4, rewrite its version header, or copy a database over a running writer. Retain the failed schema4 database even if migration/startup failed: it is diagnostic evidence and may contain later acknowledged artwork.

1. Stop Caddy, pause backup scheduling and stop/wait for the Rust writer and any active backup/restore process. Inspect the failure without exposing requests or credentials. Preserve the exact failed database and any journal/WAL companions together, release/configuration pointers, relevant bounded logs and their hashes. Do not remove the mounted data directory, the old release, pre-update backups or Caddy state.
2. Locate the activation-recorded pre-update backup and verify its hash, compatibility and accepted-art receipts against the quiet checkpoint. Restore with the pinned **prior** binary into a fresh, private directory on the data disk using `--restore-from`; never restore in place. Verify all accepted art/assets, stable IDs/ownership/memberships and expected room restart transformations before promotion. Preserve the source backup unchanged.
3. Restoration quarantines profiles, sessions, admissions and invitations. Reconcile post-backup profile revocations and membership removals before readmission; old sessions must remain revoked after readmission. If authority decisions cannot be reconstructed, keep the restore private and readmit/reinvite only reviewed accounts. Fresh Google sign-in is required; preserved linkage does not mean sessions should revive.
4. If any writes were acknowledged **after** the chosen snapshot, do not replace live authority with that older state automatically. Keep the newer database and clients' local/recovery copies, establish which accepted operations/assets are missing, and obtain a concrete reconciliation decision before promotion. Initial activation checks occur with the proxy closed specifically to avoid this rollback-loss window. Do not promise arbitrary schema4 history can be merged into schema3.
5. Only after verification/reconciliation, promote the restored database to the normal fixed data location with every writer stopped, retaining the original database and all relevant companions under an exact reviewed diagnostic path. Review the absolute source/destination paths and ownership before any move; do not move/delete the mount root or use broad cleanup patterns. Restore the prior release link and captured units/environment files, account for separate drop-ins, run systemd daemon-reload, and start the prior service with Caddy closed. The fixed data location matters because the existing backup helper also reads `/var/lib/komaphone`; changing only `--data-dir` in a unit is not a complete rollback.
6. Verify compatible readiness, quarantined access and accepted-art receipts, then reopen Caddy with compatible clients. Resume the backup timer only when it targets the promoted authority. Record actual downtime, all artifact/database/configuration pins, revoked/readmitted access and outstanding reconciliation. Retain the failed candidate and both backups until reviewed retention permits cleanup.
